# Scanning and Ingestion UI Audit

## Executive Summary

1. The scanning workflow is reachable, but it is split across at least two operator surfaces that do not share one completion contract. The project batch station completes through `completeBatchScan(...)`, while the operator scanning interface marks completion by changing local UI state and navigating away. This creates a high-impact risk that an operator believes a batch is complete while the persisted project/batch workflow is not updated (`src/features/scanning-projects/pages/ScanningStation.tsx:1182-1195`, `src/features/scanning-ops/pages/ScanningInterface.tsx:449-478`).

2. Error recovery is present only at the shallow UI-message level for several critical flows. Scan failures show banners or toasts, but pause/cancel is local-only in the project station and browser eSCL cancellation explicitly cannot cancel an in-progress scan. Operators can see that something failed, but they do not get a durable recovery path, resume point, or failed-job audit trail in the UI (`src/features/scanning-projects/pages/ScanningStation.tsx:1170-1179`, `src/features/scanning-projects/hooks/useBrowserScanner.ts:300-304`, `src/features/ingestion/components/JobQueueDashboard.tsx:29-43`).

3. Quality review exists, but quality gates are inconsistent and can be bypassed. The station blocks completion only when `needsReview` issues exist, while rejected pages and accepted-page counts are not part of the completion gate, and the QC review page can batch-approve pending samples by clearing issues with the fixed note `Batch approved`. This weakens the intended quality review flow for supervisors and operators (`src/features/scanning-projects/pages/ScanningStation.tsx:1813-1831`, `src/features/scanning-projects/pages/QCReview.tsx:327-347`).

4. Several UI paths use real APIs, but important ingestion and scanner surfaces still use simulated, local, or partial data handling. The generic batch uploader simulates per-file progress, then posts only filenames as `filePaths`, while the real ZIP bulk import uses upload plus status polling. Operators will see upload progress that is not evidence of uploaded bytes or server-side processing (`src/features/ingestion/components/BatchUploader.tsx:53-86`, `src/features/ingestion/components/BulkImportDialog.tsx:79-111`).

5. Real-time coordination is mostly polling and capped list rendering rather than a coordinated multi-station operations model. Supervisor and warehouse views poll on fixed intervals, cap or slice active batches, and present read-only status boards without assignment, escalation, or station takeover controls. Large operations can therefore hide active work from supervisors or leave coordination to out-of-band processes (`src/features/scanning-ops/api/hooks.ts:256-273`, `src/features/scanning-ops/components/SupervisorDashboard.tsx:121-179`, `src/features/scanning-ops/pages/WarehouseDashboard.tsx:83-90`).

## Recommended Fixes

1. Unify scanning completion around one persisted state machine. Route both `ScanningStation` and `ScanningInterface` through the same scan-job, page-event, QC, and batch-completion APIs; require a persisted batch id before scanning; and invalidate project, batch, page, supervisor, and operator queries after completion.

2. Add durable scan job recovery. Store active job ids in query/cache or route state, show job status after reload, expose retry/resume/cancel actions, and make browser eSCL cancellation honest by showing `cancel requested` until the device operation drains or by routing cancellation through a local scanner proxy when available.

3. Enforce quality gates in the UI before completion. Block completion when pages are rejected, unreviewed, below threshold, missing expected counts, or still marked `needs_rescan`; require reviewer notes for overrides; and preserve issue evidence instead of clearing issues during batch approval.

4. Replace simulated ingestion upload with real file upload or remove the misleading uploader. Prefer the existing ZIP bulk import pattern for real transfer/progress, or add a multi-file multipart endpoint that reports server-side per-file status and maps failures back to individual files.

5. Make supervisor oversight actionable. Add assignment/reassignment, pause/escalate, send-to-QC, requeue, and open-station controls to supervisor/warehouse boards; replace `slice` caps with pagination/search; and avoid deriving live state from only the first few projects.

6. Normalize batch status vocabulary. Pick one UI/API status set (`pending`, `in_progress`, `completed`, `failed`, `on_hold`, plus explicit QC states if needed), update cards/tables/routes to use it consistently, and add tests that every status renders a valid action state.

7. Fix cache correctness and stale query keys. Correct `useCreateQCSample` to invalidate by project id, invalidate detail/list/dashboard keys after batch completion and page mutations, and add active polling or event-driven refresh for active ingestion queues and scan jobs.

8. Improve recovery UI for queues and connectors. Add query error states, manual refresh, retry failed job, retry failed file, cancel stuck job, and download failure report controls to ingestion queues; surface connector creation errors and disable unconfigured OAuth connector submission until credentials/OAuth flow exist.

9. Reduce polling and large-batch rendering cost. Use push updates where available, lengthen inactive polling, centralize scanner/ops polling hooks, virtualize long page/batch lists, revoke object URLs on delete/unmount, and provide downsampled thumbnails/previews for large scans.

10. Add focused regression tests for the workflow gaps. Cover completion persistence, status rendering for every batch state, QC batch approval behavior, stale QC invalidation, upload-vs-simulated progress, object URL cleanup, and scan-control completion side effects.
